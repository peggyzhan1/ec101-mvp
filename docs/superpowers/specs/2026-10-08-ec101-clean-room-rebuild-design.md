# EC101 净室重建设计规格

日期：2026-10-08  
状态：待评审  
基准来源：`peggyzhan1/ec101-mvp-db_new` 的 `main` 分支与《EC101 项目现状梳理》  
目标仓库：当前空仓库 `ec101-mvp`

## 1. 目标

在不复制旧仓库历史和杂项资产的前提下，重建一个可运行、可测试、可追溯的 EC101 数据底座与费用运营台。

第一期必须打通以下纵向链路：

```text
快马 / 舟谱源文件
→ 平台转换器
→ standard.xlsx + sources.zip
→ 标准数据校验与批次入库
→ 唯一实际核算引擎
→ RESULT
→ API
→ 费用运营台只读展示
```

成功标准：业务人员能把两类平台文件转换并上传，系统能按实际核销、订单已完成和 T-2 生成逐单释放候选、活动/优惠券汇总、异常提示及 ROI 查询；所有核心数字可由自动化测试复现。

## 2. 已确认的关键决策

1. 采用净室重建，不清理或继承旧仓库的完整工作树和 Git 历史。
2. 保留现行的导入、主数据、订单、活动、优惠券和 RESULT 分层。
3. `calculation` 只有一个费用核算引擎，不存在平台分支或第二套费用口径。
4. 费用唯一事实来源是活动核销明细和优惠券核销明细中的实际金额。
5. 可释放条件只有：订单状态为“已完成”，且下单时间严格早于核算日 T-2 的 `00:00:00`。
6. 不加入理论权益重算支线，不根据活动规则反推理论优惠或理论赠品。
7. 活动规则和活动权益仍作为业务配置事实保存、查询和追溯，但不参与费用 RESULT 计算。
8. 满赠不在无确认单价时折算费用，只保留实际核销事实及数量展示能力。
9. 第一期是本地单机业务工具；认证、权限和生产数据库迁移不在本期范围。

## 3. 范围

### 3.1 保留

- 快马和舟谱源文件转换。
- 固定标准工作簿契约与版本号。
- CLI 转换核心和 Windows Tkinter 薄客户端。
- `standard.xlsx` 校验、事务入库和 `sources.zip` 元数据归档。
- 导入批次历史和 `is_current` 切换。
- 客户、商品、订单、订单行、履约、活动、活动核销、优惠券配置和券核销事实。
- 唯一实际费用核算、逐单释放候选、活动费用汇总、优惠券费用汇总和质量问题。
- 业务数据查询、筛选、详情和 CSV 导出。
- 费用总览、活动、实际费用核算、异常、可释放清单、结算候选和 ROI。
- 快马与舟谱的脱敏黄金样本和端到端回归。

### 3.2 明确排除

- 理论优惠金额、理论应赠数量和实际/理论一致性判断。
- `promotion_calculator`、`standard_promotion`、`recacl_activity_execution`、`recacl_coupon_redemption`、`consistency_of`。
- 旧库 `ec101_mvp.db`、旧 DDL、数据库备份和旧四层直灌脚本。
- `raw_*`、`std_*`、`tpm_*` 旧表。
- 原始真实业务文件、历史试点目录、截图、PPT、临时输出、探查脚本、缓存和构建残留。
- 财经云接入、用户认证、RBAC、异常协同、支付、ERP 上账和生产多租户部署。
- 没有后端事实支撑的静态指标、假状态和假操作。

## 4. 架构

```text
src/ec101/contract      标准工作簿契约、类型和基础校验
src/ec101/converters    快马、舟谱平台适配
src/ec101/importing     批次、事务、事实入库、归档元数据
src/ec101/calculation   唯一实际费用核算引擎
src/ec101/reporting     ROI、核验报告和导出
src/ec101/api           HTTP 路由、请求校验和查询
db                      SQLite DDL 与迁移
desktop                 Windows 转换器薄客户端
web                     React 费用运营台
tests                   单元、集成、端到端和脱敏样本
docs                    数据契约、核算口径和运行说明
```

模块边界：

- 转换器只产生标准工作簿和归档，不连接数据库。
- 导入服务只校验和写入事实，不写 RESULT。
- 核算引擎只读取已入库事实，不读取 Excel、不识别平台。
- API 不重新计算费用，只调用核算服务或读取已保存 RESULT。
- 前端不计算 T-2、优惠金额或 ROI，只展示 API 结果。

## 5. 数据流

1. 业务人员选择平台和源文件。
2. 平台转换器把字段和语义映射为统一工作簿。
3. 转换器输出 `standard.xlsx`、`sources.zip` 和转换报告。
4. 导入服务先完成全量校验，再在一个事务中写入导入批次和业务事实。
5. 同一经销商、平台、覆盖区间再次导入时，旧批次 `is_current=0`，新批次 `is_current=1`；其他覆盖区间和其他经销商不受影响。
6. 导入成功后，API 显式调用唯一核算引擎并传入核算日。
7. 核算引擎追加一次 `calculation_run`，写入逐单候选、活动汇总、券汇总和质量问题。
8. 当前模式对每个 `is_current=1` 的导入批次读取最新一次核算；历史模式固定读取指定核算批次。

## 6. 唯一实际核算引擎

### 6.1 输入和输出

输入：SQLite 连接、`import_batch_id`、可选 `calc_date`。  
输出：新建的 `calculation_run_id`。  
事务：核算运行、全部明细和汇总必须原子写入；失败时不得留下半个 RESULT。

### 6.2 核算日和截止时间

- `calc_date` 缺省为运行当天。
- 非 `YYYY-MM-DD` 格式直接拒绝。
- `release_cutoff = calc_date 00:00:00 - 2 days`。
- `order_time < release_cutoff` 才算达到 T-2；等于截止时间仍不可释放。

### 6.3 实际费用来源

活动费用：

```text
activity_benefit = SUM(activity_execution.discount_amount)
```

优惠券费用：

```text
coupon_benefit = SUM(coupon_redemption.discount_amount)
```

订单行 `discount_amount` 只用于业务展示和对照，不进入费用 RESULT。

### 6.4 参与订单

订单满足任一条件即为参与订单：

- 至少存在一条关联的活动核销明细；
- 至少存在一条已关联订单的优惠券核销明细。

同一订单存在多条核销记录时，金额求和，但参与订单数和释放订单数必须按 `order_id` 去重。

### 6.5 可释放规则

```text
is_candidate =
  order_status == "已完成"
  AND order_time IS NOT NULL
  AND order_time < release_cutoff
```

不可释放原因：订单状态不符、下单时间缺失或未达 T-2。每个参与订单写一条 `release_candidate`。

### 6.6 未关联优惠券

- 所有券核销金额计入批次的券实际核销总额。
- 没有唯一关联订单的券不能进入释放候选。
- 券汇总必须分别记录总核销、已关联、可释放和未关联的数量及金额。
- 未关联券产生质量问题，但不影响其他订单和活动的核算。

### 6.7 活动与优惠券汇总

活动按 `activity_id` 汇总：实际核销金额、去重参与订单、去重可释放订单、可释放金额、待释放订单和待释放金额。

优惠券按 `coupon_config_id` 汇总：使用数量/金额、已关联金额、可释放数量/金额、未关联数量/金额。

满赠的实际核销金额通常为零。第一期不使用活动规则推导应赠数量，也不以未确认单价生成结算金额。

### 6.8 质量问题

第一期仅产生基于实际事实的质量问题：

- 未达释放节点（提示）；
- 券无法关联订单（警告）；
- 核销记录缺少必要标识或金额（导入阶段阻断或警告）；
- 同一核销记录无法唯一关联（警告）。

不得产生“理论权益与实际执行不一致”等理论重算问题。

### 6.9 明确禁止

唯一核算引擎不得：

- 读取 `activity_rule` 或 `activity_benefit` 反推费用；
- 调用任何促销模板计算器；
- 计算 theoretical、entitled 或 consistency；
- 根据平台名称分支；
- 从订单行优惠字段替代核销事实；
- 在 API 或前端重复实现核算规则。

## 7. 数据库

### 7.1 保留的业务事实表

导入审计：`import_batch`、`import_file`、`import_validation_issue`。  
主数据：`dealer_platform`、`customer`、`product`。  
订单履约：`order_header`、`order_line`、`fulfillment`。  
活动：`activity`、`activity_rule`、`activity_benefit`、`activity_scope`、`activity_execution`。  
优惠券：`coupon_config`、`coupon_issue_rule`、`coupon_use_rule`、`coupon_scope`、`coupon_redemption`。

### 7.2 RESULT 表

- `calculation_run`
- `release_candidate`
- `activity_fee_summary`
- `coupon_fee_summary`
- `calculation_quality_issue`

不创建 `entitlement_check`。`calculation_run` 不包含 `theoretical_activity_benefit`、`theoretical_coupon_benefit` 或 `consistent_orders`。

### 7.3 数据库纪律

- 仓库不提交运行时 `.db`、备份库或真实业务数据。
- 使用 DDL 加 `PRAGMA user_version` 管理结构版本。
- 每次测试从空库创建结构，不依赖预置数据库。
- 开启 `PRAGMA foreign_keys=ON`。
- 为当前批次、订单关联和核算查询建立必要索引。
- 结构测试必须断言表、关键列、外键和唯一约束。

## 8. API

第一期保留以下能力，路径可与旧接口兼容：

- 健康检查。
- 创建、列出和查看导入批次。
- 查看导入校验问题和逐单释放清单。
- 查询订单、订单行、活动、活动核销、客户、商品和履约。
- 查询费用总览、活动汇总、券汇总、质量问题、结算候选和 ROI。
- CSV/Excel 导出。

列表接口统一支持分页；无效批次返回明确错误，不静默回退到最新数据。

## 9. 前端

第一期导航：

- 数据接入
- 业务数据
- 运营总览
- 活动费用
- 优惠券费用
- 实际费用核算
- 证据与异常
- 核销与对账
- ROI 分析

所有指标必须来自 API。没有真实后端状态的页面、数字和操作不进入新项目。

## 10. 测试与验收

### 10.1 单元测试

- 核算日期格式和 T-2 边界。
- 已完成、非已完成、缺失时间和恰好等于截止时间。
- 同订单多条核销记录的金额汇总与订单去重。
- 活动与优惠券金额严格来自核销表。
- 未关联优惠券不会释放。
- 引擎源码不包含平台名称、理论字段或促销重算依赖。

### 10.2 集成测试

- 合法工作簿导入后事实完整。
- 校验失败时事务回滚。
- 重复覆盖区间正确切换 `is_current`。
- 导入和核算是两个边界清晰的步骤。
- 一次核算原子写入运行、候选、汇总和问题。
- 多次核算保留历史且当前查询读取最新运行。

### 10.3 黄金回归

快马兴路强核算日 `2026-09-22`：

- 满减参与订单 136；实际核销 2040。
- 可释放订单 133；可释放金额 1995。
- 不可释放 3 单、45 元。
- 满赠 98 单。
- 测试券实际核销 200。

舟谱羿柏：

- 返券和满赠必须以各自实际核销事实进入标准库。
- 券核销总额、已关联金额、未关联金额和可释放金额分别可追溯。
- 不把返券误判为金额满减。

黄金样本必须脱敏并缩减到足以证明口径的最小集合；如完整数字必须依赖真实数据，则在本地验收脚本中使用外部样本，仓库只保存期望值和样本格式。

## 11. 净室迁移规则

可以迁移：已经确认的字段契约、实际核算公式、API 语义、脱敏测试断言和必要的 UI 信息架构。

不得直接迁移：旧数据库、原始试点文件、输出物、探查脚本、并行核算器、历史归档工具、大型单文件页面或服务器文件。

迁移每个模块时先写面向新接口的测试，再实现满足测试的最小代码。旧代码只能作为行为证据，不能整目录复制。

## 12. 实施顺序

1. 建立仓库骨架、依赖和 CI。
2. 建立标准工作簿契约、SQLite DDL 和结构测试。
3. 完成最小导入服务和批次切换。
4. 完成唯一实际核算引擎及 RESULT 集成测试。
5. 以快马完成第一个端到端纵向切片。
6. 增加舟谱转换适配并运行第二个平台回归。
7. 实现查询 API、导出和 ROI。
8. 实现精简费用运营台。
9. 增加 Windows 桌面转换壳、完整验收和交付文档。

每一步必须产生可独立运行和验证的结果，不提前建设生产权限、多租户或外部集成。

## 13. 完成定义

- 新克隆仓库不需要任何旧数据库即可运行测试。
- 快马和舟谱均能完成转换、导入、核算、查询和展示。
- 实际核销金额是唯一费用来源。
- 代码中不存在理论权益重算支线或第二核算器。
- RESULT 能追溯到核算批次、导入批次、订单和核销事实。
- 黄金数字、边界条件和历史回放均由自动化测试覆盖。
- 仓库不含真实业务数据、数据库文件、备份、缓存和生成输出。
- README、PROJECT、数据字典和实际代码口径一致。

## 14. 已知风险

- 舟谱双单号和未关联券需要用脱敏样本锁定关联优先级。
- 旧代码按核销记录统计活动订单，新实现必须按订单去重；黄金数字需要确认不受重复记录影响。
- 旧引擎没有写入 `coupon_fee_summary`，新实现必须补齐实际券汇总并通过端到端测试。
- 真实试点文件不能进入新仓库，完整黄金验收需要约定外部样本的本地路径或交付方式。
- 第一期使用 SQLite 和本地 HTTP 服务，不代表已满足多人生产部署要求。
